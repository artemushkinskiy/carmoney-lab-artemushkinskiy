# План MILEAGE: «пробег > 400 000 км → решение review»

ID задачи: `MILEAGE`. Источник: `docs/sources/client_note.md` (строки 24, 40), `docs/setup/code_map.md` (раздел «Куда встанет правило»). Требования: `docs/intent/intent_MILEAGE.md` и `docs/spec/spec_MILEAGE.md` (REQ-MILEAGE-01…05, AC-MILEAGE-01…06).

Сверено со спекой. Дополнения против предыдущей версии плана:

- `ApplicationValidator` вошёл в правки: обязательность пробега (`''` → ошибка валидации). Прежняя формулировка «валидацию не трогаем, `''` проходит как 0 км» противоречила REQ-MILEAGE-05.
- Переопределение решения — только при `approve` (раньше — безусловно; безусловное смягчало бы reject и нарушало baseline OQ-1).
- Добавлены тесты AC-04 (LTV-review + 400 001), AC-05/06 (отсутствует/null/`''`), регрессия `mileage => 0` и фиксатор диапазона 500 001.
- Вопросы заказчику получили статусы «закрыт / перенесён аналитику» (раздел 5).

## 1. Файлы — что и где меняем

- `backend/config/rules.php` — секция `vehicle`: добавить `'review_mileage_km' => 400000` (порог решения, REQ-MILEAGE-01…03; `max_mileage_km = 500000` — порог валидации — не трогаем, spec «не входит»).
- `backend/src/Domain/AssessmentService.php` — в `assess()` после строки 33 (`$decision = $this->decisionEngine->decide($ltv);`) переопределить `$decision = DecisionEngine::REVIEW`, если `$decision === DecisionEngine::APPROVE` и `$input['mileage'] > review_mileage_km` (REQ-MILEAGE-02). До расчёта `approved_limit`, поэтому лимит при понижении — 0 (baseline OQ-2).
- `backend/src/Domain/ApplicationValidator.php` — обязательность пробега (REQ-MILEAGE-04/05): до приведения `(int)` проверить «пусто» (ключ `mileage` отсутствует, `null` или `''`) → ошибка валидации по ключу `mileage`; `mileage = 0` остаётся валидным; диапазон 0–500 000 (`max_mileage_km`) не меняем.
- `tests/Unit/AssessmentServiceTest.php` — тесты правила пробега, блок «решение» в разделе 3; `payload()` расширить параметром `mileage` с умолчанием 96 000 (существующие тесты не меняются).
- `tests/Unit/ApplicationValidatorTest.php` — тесты обязательности пробега и фиксаторы диапазона, блок «валидация» в разделе 3.
- `docs/setup/code_map.md` — после реализации обновить разделы «Куда встанет правило» и «Что сейчас проверяется про пробег» (пробег теперь участвует в решении; пустая строка — ошибка).

Не меняем: `DecisionEngine` (сигнатура `decide(float $ltv)` остаётся), `ApplicationRepository`, `db/*`, фронтенд, Http-слой (формат ответа не меняется: причина review не добавляется — spec «не входит»), `max_mileage_km`.

## 2. Шаги реализации по порядку

1. Добавить `'review_mileage_km' => 400000` в `backend/config/rules.php` (секция `vehicle`, рядом с `max_mileage_km`, комментарий: порог решения, а не валидации). Число 400 000 — intent §3 / spec; в коде читаем из конфига, не хардкодим (AGENTS.md).
2. `ApplicationValidator`: проверка «пробег обязателен» до `(int)`-каста — ключ отсутствует / `null` / `''` → `$errors['mileage']` (например, «Пробег обязателен»; текст сообщения спека не фиксирует). `0` валиден, диапазон 0–500 000 без изменений (REQ-MILEAGE-04/05, AC-05/06).
3. `AssessmentService::assess()`: после `decide($ltv)` — при `$decision === DecisionEngine::APPROVE` и пробеге больше `review_mileage_km` записать `$decision = DecisionEngine::REVIEW` (REQ-MILEAGE-02). `review` и `reject` не переопределяем: review уже review (REQ-MILEAGE-03), reject не смягчаем (baseline OQ-1).
4. Написать тесты из раздела 3 в оба тестовых файла по конвенциям PHPUnit 11 (AAA, имя метода описывает поведение, `#[DataProvider]`).
5. Прогнать `make test` и `make lint`, убедиться в зелёном.
6. Обновить `docs/setup/code_map.md`.

## 3. Тесты

Числа и источники: порог 400 000 км — intent §3 / spec; LTV-примеры — 450 000 / 900 000 = 50% (< 60 → approve), 700 000 / 900 000 ≈ 77,78% (60–85 → review, как в AC-04), 855 000 / 900 000 = 95% (> 85 → reject); пороги LTV — `rules.php:44-45`; диапазон валидации пробега 0–500 000 — `rules.php:23` (`max_mileage_km`).

Блок «решение» — `tests/Unit/AssessmentServiceTest.php`, вход через `assess()`:

- 399 999 км при LTV-approve (450 000 / 900 000) → решение `approve`, `approved_limit` = 450 000 (AC-01).
- 400 000 км при LTV-approve → решение `approve`, `approved_limit` = 450 000 — граница включена (AC-02).
- 400 001 км при LTV-approve → решение `review`, `approved_limit` = 0 — baseline плана (AC-03; лимит спекой не зафиксирован, OQ-2).
- 400 001 км при LTV-review (700 000 / 900 000) → решение `review` (AC-04).
- 400 001 км при LTV-reject (855 000 / 900 000) → решение `reject` — baseline плана: пробег понижает только approve (спека случай reject не фиксирует, OQ-1).
- `mileage => ''` → `ValidationException` до расчёта решения (AC-06; сегодня `''` проходит как 0 км — поведение меняется).

Блок «валидация» — `tests/Unit/ApplicationValidatorTest.php`:

- Ключ `mileage` отсутствует → `ValidationException`, в ошибках есть ключ `mileage` (AC-05).
- `mileage => null` → `ValidationException`, ключ `mileage` (AC-05).
- `mileage => ''` → `ValidationException`, ключ `mileage` (AC-06).
- `mileage => 0` → валидно (0 — не «пусто», остаётся допустимым значением; регрессия после шага 2).
- `mileage => 500001` → `ValidationException` (диапазон валидации 0–500 000 не изменился — spec «не входит»).

## 4. Риски

- **OQ-1 (LTV-reject + пробег > 400 000), перенесён аналитику**: реализуем baseline «reject не смягчается» — переопределение только при `approve`; тест-фиксатор 400 001 + LTV-reject → `reject`. Если аналитик решит иначе — правится одно условие и один тест.
- **OQ-2 (лимит при понижении), перенесён аналитику**: переопределение стоит до расчёта лимита, поэтому `approved_limit = 0`, как у обычного review (вариант из формулировки вопроса); тест фиксирует 0. При ответе «предварительный лимит» — менять точку переопределения.
- **OQ-3 (границы задачи), перенесён аналитику**: рабочее ожидание — `max_mileage_km` (500 000), LOAN-12, БД, фронтенд, CASE-08 не трогаем; тест-фиксатор 500 001 → ошибка валидации.
- **Пустая строка против нуля**: `(int)'' = 0` — проверку «пусто» делать до каста, иначе `''` неотличим от валидного 0; после правки 0 обязан остаться валидным (тест `mileage => 0`).
- **`max_mileage_km = 500 000`**: заявки с пробегом > 500 000 отбрасываются валидацией и до решения не доходят — правило фактически сработает в диапазоне 400 000 < mileage ≤ 500 000; порог валидации в этой задаче не трогаем.
- **Фронтенд**: пустое поле пробега в форме раньше нормализовалось в 0 км (возможен approve), теперь заявка отклоняется ошибкой валидации (422) — ожидаемо по REQ-MILEAGE-05; фронт не меняем.
- **Обратная совместимость**: существующие тесты используют mileage 96 000 (`AssessmentServiceTest`) и 84 000 (`ApplicationValidatorTest`), сид — 84 000; `payload()` расширяется параметром с умолчанием 96 000, существующие тесты не меняются. Формат ответа API не меняется.
