# План MILEAGE: «пробег > 400 000 км → решение review»

ID задачи: `MILEAGE`. Источник: `docs/sources/client_note.md` (строки 24, 40), `docs/setup/code_map.md` (раздел «Куда встанет правило»).

## 1. Файлы — что и где меняем

- `backend/config/rules.php` — в секцию `vehicle` добавить `'review_mileage_km' => 400000` (порог решения; не трогаем `max_mileage_km`).
- `backend/src/Domain/AssessmentService.php` — в `assess()` после строки 33 (`$decision = $this->decisionEngine->decide($ltv);`) переопределять `$decision` на `DecisionEngine::REVIEW`, если `$input['mileage'] > review_mileage_km`.
- `tests/Unit/AssessmentServiceTest.php` — новые тесты правила пробега (граничные значения + пустой пробег).
- `docs/setup/code_map.md` — после реализации обновить раздел «Что сейчас проверяется про пробег» (в решении теперь участвует и пробег).

Не меняем: `DecisionEngine` (сигнатура `decide(float $ltv)` остаётся), `ApplicationValidator`, `ApplicationRepository`, `db/*`, фронтенд.

## 2. Шаги реализации по порядку

1. Добавить порог `review_mileage_km => 400000` в `backend/config/rules.php` (секция `vehicle`, рядом с `max_mileage_km`, с комментарием, что это порог решения, а не валидации).
2. В `AssessmentService::assess()` после получения `$decision` от `DecisionEngine` сравнить `$input['mileage']` с порогом; при превышении записать `$decision = DecisionEngine::REVIEW`.
3. Решить приоритет конфликта (см. Риски): baseline-вариант — `reject` по LTV не смягчается пробегом, правило действует только на `approve`.
4. Написать тесты (раздел 3) в `tests/Unit/AssessmentServiceTest.php` по конвенциям PHPUnit 11 (AAA, `#[DataProvider]`).
5. Прогнать `make test` и `make lint`, убедиться в зелёном.
6. Обновить `docs/setup/code_map.md`.

## 3. Тесты

Файл `tests/Unit/AssessmentServiceTest.php`, данные через `#[DataProvider]`, mileage подмешивается в `payload()`:

- 399 999 км при LTV-`approve` (например, 450 000 / 900 000) → решение остаётся `approve`, лимит = запрошенной сумме.
- 400 000 км при LTV-`approve` → решение остаётся `approve` (граница включена: «не больше 400 000»).
- 400 001 км при LTV-`approve` → решение `review`, лимит 0.
- 400 001 км при LTV-`reject` (например, 855 000 / 900 000) → решение `reject` (пробег не смягчает reject — фиксирует выбранный приоритет).
- Пустой пробег (ключ отсутствует, `mileage => null`) → `ValidationException` с ошибкой `mileage` до расчёта решения (текущее поведение: `?? -1` → ошибка диапазона).
- Пустая строка `mileage => ''` → сегодня `(int)''` нормализуется в 0 и проходит как 0 км (см. Риски; тест фиксирует фактическое поведение, вопрос заказчику — в разделе 5).

## 4. Риски

- **Существующая проверка `max_mileage_km = 500000`**: заявки с пробегом > 500 000 отбрасываются валидацией и до решения не доходят — новое правило фактически сработает только в диапазоне 400 000 < mileage <= 500 000. Если поднять/убрать `max_mileage_km`, изменится зона действия правила — трогать его в этой задаче не будем.
- **Приоритет конфликтов**: механизм комбинирования правил решения отсутствует; `LTV-reject + пробег-review` — что должно победить, в коде не определено. Без ответа заказчика берём вариант «reject не смягчается» (пробег понижает только `approve`).
- **`approved_limit`**: при `approve` по LTV и `review` по пробегу лимит должен стать 0 — переопределение стоит до расчёта лимита в `assess()`, иначе лимит останется ненулевым.
- **Пустая строка пробега**: `(int)''` = 0 — заявка с «пустым» одометром проходит как 0 км и получает `approve`; возможно, стоит требовать явный 0 или отдельную ошибку.
- **Обратная совместимость**: существующие тесты `AssessmentServiceTest` используют mileage 96 000 — не задеты; seed/фронт с 84 000 — не задеты.
- **Не входит в задачу**: LOAN-12 (лимит по `ltv_by_age`), изменения валидации пробега, БД и фронтенда, сверка пробега с внешним справочником по VIN (CASE-08).

## 5. Вопросы к заказчику

1. При LTV-`reject` и пробеге > 400 000 — оставляем `reject` или смягчаем до `review`?
2. Граница «не больше 400 000» — при ровно 400 000 решение не меняется; подтвердить, что 400 000 — это `approve` (если LTV позволяет).
3. Пустая строка в поле пробега сейчас превращается в 0 км — допустимо или нужна ошибка валидации «пробег обязателен»?
4. Пробег 400 001–500 000 при LTV-`approve`: лимит точно 0 (как у обычного `review`), или считаем предварительный лимит?
5. Нужно ли отражать причину `review` в ответе API (сейчас решение — одна строка без обоснования)?
